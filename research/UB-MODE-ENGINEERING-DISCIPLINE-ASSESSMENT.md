## 1. Назначение и границы

Цель — определить, добавляет ли адаптация **ub-mode** Роберта К. Мартина (Robert C. Martin, Uncle Bob) измеримую ценность VeriLayer Method как (a) процедура критического пересмотра исходных предпосылок и (b) воспроизводимые свидетельства качества реализации L4.

**Исходный проект:** [unclebob/ub-mode](https://github.com/unclebob/ub-mode), [README](https://github.com/unclebob/ub-mode/blob/master/README.md), [SKILL.md](https://github.com/unclebob/ub-mode/blob/master/SKILL.md); рассмотренная версия SKILL: blob `9ac940b23b61d77e8e5192721d7b6066357f892c`. Исходный проект распространяется по MIT License, copyright © 2026 Robert C. Martin. Автор проекта указывает, что правила частично и свободно основаны на работе [@poteto](https://github.com/poteto) (`poteto-mode` / `pstack`). Благодарим обоих авторов за опубликованные идеи; это признание источников **не означает** их участие, соавторство или одобрение VeriLayer.

**Не предлагаем:** копировать полный `SKILL.md`, делать ub-mode обязательным, добавлять тринадцатый Stop Gate, принимать CRAP/дублирование/мутации за доказательство системной корректности, менять лицензии VeriLayer или объявлять экспериментально подтверждённую пользу.

## 2. Что фактически представляет собой ub-mode

**First Make it Work:** минимальное изменение; корректная форма данных; TDD с наблюдением ожидаемого сбоя; пересмотр архитектуры «с первых принципов»; `Attack the Premise`; `Subtract Before You Add`; достижение проверяемого результата; выделение повторяемого инструмента; моделирование домена, границы, типы, идемпотентность и владение изменяемым состоянием.

**Then Make it Right:** устранение первопричин; маленькие проверяемые порции; поведенческие тесты; оценка сложности/покрытия через Crapper; поиск похожих реализаций через Dryer; мутационные тесты через Mutator; рефакторинг с сохранением поведения.

**Practice:** журнал действий и причин; сохранение компактного контекста; очистка рабочих деревьев; небольшие коммиты и push.

Это **инструкции агенту + сопутствующие проверяющие инструменты**, а не полноценная методология проверки проектных решений L0–L5. Наличие инструкции или результата инструмента не равнозначно принудительному обеспечению полномочий агента.

## 3. Матрица соответствия VeriLayer

| Принцип / механизм ub-mode | Уровень / объект VeriLayer | Что уже есть | Исследуемое дополнение | Ограничение |
|---|---|---|---|---|
| Минимальная работающая правка | L4, P7, risk profile | Локальность gates и risk tailoring | Ограничение объёма изменений | Не оптимизировать размер diff в ущерб архитектуре |
| TDD и наблюдаемый failing test | L3–L4, VO, run status | Design ↔ Verifiability, исполняемые тесты по мере появления кода | Явная последовательность RED → GREEN → REFACTOR | Ложные или непроверяемые тесты не обязательны; RED — не системное evidence |
| Test Behavior, Not Implementation | L3–L5, oracle | Проверка оракулов и scope | Поведенческие тест-кейсы, устойчивые к рефакторингу | Без слепоты к необходимым внутренним инвариантам |
| Model Domain / Type Discipline | L1–L4, contracts | Архитектурные границы, инварианты | Условия допустимых состояний и валидация на входе | Статическая типизация не универсальна для всех стеков |
| Idempotence / mutable state ownership | L2–L5 | Контракты, ошибки, negative scenarios | Проверки повторов, crash recovery и гонок при наличии риска | Не навязывать распределённую сложность простому приложению |
| Attack the Premise | L0–L3, CAR, VO | TRIZ contradiction resolution, S02–S04, S11 | **Premise Challenge** при повторных сопоставимых отказах | Повторная ошибка не доказывает ложность предпосылки |
| Redesign from First Principles | L1–L3, CAR | Пересмотр design при существенном конфликте | Структурированное сравнение локального патча и редизайна | Не превращать локальные баги в полный редизайн |
| Subtract Before You Add | L2–L4 | Risk tailoring | Эвристика удаления избыточных обязанностей | Удаление не должно нарушать контракты |
| Crapper / Dryer / Mutator | L4, EvidenceRecord | Unit/static analysis/review; формализованные evidence | **Implementation Quality Profile** | Метрики — частичные прокси, не оракулы корректности |
| UML Viewer | L1–L2 / L4 | ADR, анализ зависимостей | Экспериментальный анализ архитектуры как гипотезы | Картинка, построенная по коду, не доказывает правильности требований |
| Log / ordered commits | Provenance, Handoff | EvidenceRecord, трассировка | Привязка действий к claim/VO/change | Журнал агента — evidence действия, не результата |
| Push to main / cleanup | S10, полномочия | Строгие ограничения опасных операций | **Не переносить без разрешительной модели** | Возможны необратимые последствия |

**Позиция:** ub-mode полезнее всего в L4 и при возврате от неудачного L4 evidence к L0–L3. Это не замена вертикальной модели VeriLayer и не свидетельство её экспериментальной эффективности.

## 4. Гипотеза H-P: Premise Challenge

**Проблема.** Агент может многократно исправлять симптомы, не пересматривая скрытую предпосылку: например, «операция записи всегда атомарна», «один процесс означает отсутствие конкуренции», «проверка на mock подтверждает production-поведение».

**Предложение (авторская адаптация, не термин ub-mode):** `Premise Challenge` — исследовательская процедура анализа допущений, запускаемая, когда две или более независимые/последовательные попытки, основанные на **одной явно установленной предпосылке**, дают сопоставимые отрицательные результаты. Число «две» — **эвристика для пилота**, не универсальное правило и не основание для автоматического Stop Gate.

### PC-1…PC-7: пример операционного протокола

1. **Сопоставить** фактические результаты run: `EXECUTED_FAIL`, `INFRA_BLOCKED`, `INCONCLUSIVE`; исключить смешение дефекта и сбоя инфраструктуры.
2. **Назвать** общую предпосылку одним проверяемым предложением; сохранить её источник и уровень происхождения (L0–L3).
3. **Разделить альтернативные причины:** неверный оракул, дефект среды, ошибка реализации, неверный контракт, неверное доменное допущение.
4. **Спроектировать опровергающую проверку** с условиями, которые различают альтернативы; создать/уточнить соответствующий VO.
5. **Сформировать варианты:** локальная правка; изменение контракта/дизайна; снятие предпосылки; при материальном конфликте — штатный процесс CAR/TRIZ.
6. **Оценить blast radius:** зависимые claims, изменённые версии объектов, действительность прежних evidence; применить **существующие** S04/S06/S07/S08/S11 по их условиям.
7. **Зафиксировать результат:** предпосылка подтверждена / опровергнута / не определена, scope, evidence, решение и следующий допустимый шаг.

**Важно:** PC не предоставляет новых полномочий, не превращает количество неудач в доказательство, не отменяет требования к oracle или различение статусов run/VO/gate/action.

### Мини-кейс To-Do List

Требование: после сбоя приложение не должно терять ранее подтверждённые задачи.

- Предпосылка L2: «одновременных записей не бывает, приложение однопользовательское».
- L4: тест восстановления после аварийного завершения выявляет потерю данных; повторная попытка исправления интерфейса хранения не помогает.
- PC: различить отсутствие конкурирующих пользователей и отсутствие конкурирующих операций внутри процесса. Отдельно проверить атомарность записи, flush/sync и восстановление.
- VO: «подтверждённая задача сохраняется после моделируемого сбоя в заданной среде»; evidence — fault-injection + проверка фактического хранилища.
- Негативный исход: повторный сбой вызван некорректным тестовым fixture, а исходное допущение остаётся неподтверждённым. PC должен приводить к INVESTIGATE, а не автоматически к глобальному редизайну.

### Как может быть опровергнута H-P

Дополнительная процедура не снижает число повторных неудачных исправлений, не помогает найти первопричины или повышает стоимость принятого изменения и False Stop больше заранее допустимого порога.

## 5. Гипотеза H-Q: Implementation Quality Profile (L4)

**Предложение:** необязательный, риск-ориентированный пакет свидетельств уровня реализации. Он **не является отдельной осью статуса** и не заменяет L5 acceptance.

### 5.1 Инструменты и их сигналы

| Инструмент | Источник | Измеряет | Зафиксированное в источнике правило | Что НЕ следует утверждать |
|---|---|---|---|---|
| **Crapper** | [unclebob/crapper](https://github.com/unclebob/crapper) | Cyclomatic complexity + coverage → CRAP | В ub-mode: CRAP < 10 на функцию; в README инструмента обычно обсуждаются более широкие диапазоны риска | Низкий CRAP не доказывает отсутствия багов; покрытие — не correctness |
| **Dryer** | [unclebob/dryer](https://github.com/unclebob/dryer) | Структурная похожесть | В ub-mode указан порог ≥ 0.8; **в CLI README default 0.82** | Похожесть не доказывает, что объединение кода целесообразно |
| **Mutator** | [unclebob/mutator](https://github.com/unclebob/mutator) | Killed/survived/uncovered mutants | Исходный skill требует устранять survivors и непокрытое | Не каждый survivor — исправимый дефект теста; эквивалентные/некорректные мутации требуют классификации |
| **UML Viewer** | [unclebob/uml-viewer](https://github.com/unclebob/uml-viewer) | Зависимости компонентов, структурные ограничения, наложение метрик | Интерактивные UML-проекции и архитектурные предложения | Совпадение диаграммы с исходниками не доказывает соответствия исходному замыслу |

Для Crapper опубликована формула `CRAP = CC² × (1 - coverage)³ + CC`, где `coverage` — доля от 0 до 1 (а не процент от 0 до 100). Это **эвристика риск-приоритизации**, не вероятность отказа.

В README инструментов заявлена поддержка Clojure, Java, Go, TypeScript, Rust и Python. Это заявление об охвате, **не проверенная нами точность**. На пилоте потребуется фиксировать версии, зависимости, язык, тип coverage и отклонения результатов. Особенно тщательно сверять branch vs line coverage и привязку данных после переименования функций.

### 5.2 Предлагаемые уровни применения (не норматив)

| Risk profile | Минимум | Опциональная аналитика | Реакция |
|---|---|---|---|
| Lite | Поведенческие тесты по критичным функциям, обычный CI | Complexity review по изменённым функциям | Review/INVESTIGATE, без глобального запрета |
| Standard | Тесты + релевантные coverage/complexity, анализ дубликатов при устойчивом росте | Мутации для изменённого рискованного модуля | Точки блокирования только по заранее согласованным VO |
| Critical | Согласованные fault/negative tests, независимый oracle review и source-of-truth для результатов | Охват мутациями + анализ зависимостей | Детерминированный gate для заранее объявленных обязательных проверок; human authority для опасных действий |

Числовые пороги **не объявлять универсальными**, пока не измерены ошибки классификации и стоимость: чрезмерно строгие пороги ухудшают throughput. Если проект назначил порог обязательным, его должен определить владелец на основании риска/контракта; изменение этого условия требует обычного change control (S09).

### 5.3 Предлагаемая форма evidence (пример, не новая нормативная схема)

```yaml
id: EV-L4-Q-001
claim_id: VO-TODO-ATOMIC-WRITE
artifact: src/storage.py
artifact_version: "<commit-sha>"
level: L4
instrument: mutator
instrument_version: "<pinned-version>"
run_status: EXECUTED_PASS     # only if the declared check really executed and passed
command: "<exact-command>"
environment: "<OS, Python, dependencies>"
oracle_and_test_suite: "<test-suite-id/version>"
result:
  killed: 18
  survived: 2
  uncovered: 1
limitations:
  - "mutation score is partial and does not establish crash recovery"
raw_report_ref: "<immutable-report-link-or-hash>"
reviewer: "<reviewer-id>"
```

**Важное уточнение:** этот пример иллюстрирует структуру, а не реальный прогон. Числа синтетические; `EXECUTED_PASS` допустим только относительно **заранее объявленного** критерия. При обязательном требовании «нет surviving mutants» приведённый результат был бы `EXECUTED_FAIL`, а не `EXECUTED_PASS`. Для корректности можно использовать `INCONCLUSIVE`, если завершение проверки не позволяет оценить критерий.

Обязателен учёт *эквивалентных мутаций*, некорректных трансформаций, тайм-аутов, недоступных сайтов и несовпадения тестовых окружений. По умолчанию не складывать `uncovered` с `survived` и не считать `NOT_RUN` успешной проверкой.

## 6. Модель решений и безопасность

**Не менять S01–S12.** Указанные сигналы могут стать evidence для конкретного VO, но только с заранее согласованными критерием, scope и ответственным.

| Ситуация | Корректное поведение VeriLayer |
|---|---|
| Crapper > 10 в некритичном модуле | Замечание/исследование; не автоматический HARD Stop |
| Обнаружен похожий код по Dryer | Рассмотреть причины дублирования; не проводить автоматическое объединение |
| Survivor при мутации | Проверить качество oracle, эквивалентность и покрытие; не автоматически признать весь продукт некорректным |
| Fail обязательного теста для VO | `EXECUTED_FAIL` и S07 на **зависимое действие** |
| Инструмент не смог запуститься | `INFRA_BLOCKED` / `NOT_RUN`, применить S08 к зависимому действию; не выдавать PASS |
| UML показывает нарушение инварианта | Проверить достоверность модели, источник инварианта и scope; при подтверждении S03 |
| Агент предлагает push в main / удаление данных | Не выполнять без согласованного уровня полномочий и независимого enforcement; S10 по условиям |

В ub-mode `SKILL.md` есть формулировки о push в основную ветку и очистке worktree. Они уже оспариваются в [upstream Issue #2](https://github.com/unclebob/ub-mode/issues/2). В нашем возможном адаптере **никаких автоматических push-to-main, delete/cleanup, обходов branch protection, изменения approval или отключения тестов**. Допустимый сценарий: отдельная ветка → diff → проверки → PR → предусмотренное политикой подтверждение. Инструкция LLM **не обеспечивает** фактическую авторизацию.

UML Viewer содержит агентную интеграцию с повышенными разрешениями и установочные сценарии. Прежде чем использовать, требуется кодовый и supply-chain review, закрепление версии и изоляция исполнения; **не запускать установочные скрипты из сети в доверенной среде без аудита**.

## 7. Эксперимент: сравнение дисциплин разработки

**Тип:** дополнительная *exploratory* абляция, **не часть уже предрегистрированного (проектируемого) исследования v0.5**. Перед запуском зафиксировать задачи, конфигурации, primary outcomes, пороги успеха и процедуру независимой оценки; затем оформлять отдельное дополнение к [EXPERIMENT_PROTOCOL.md](../EXPERIMENT_PROTOCOL.md).

### 7.1 Варианты (пилотная сетка, не переименовывать основные A–E)

| Arm | Workflow | Что проверяем |
|---|---|---|
| Q-A | Обычный агент + добросовестные стандартные инженерные инструкции | Базовый уровень |
| Q-B | Тот же агент + оригинальный ub-mode, но с одинаковыми внешними правами/запретами | Эффект режима ub-mode |
| Q-C | VeriLayer Core L0–L5 + VO/evidence + S01–S12 без нового профиля | База VeriLayer |
| Q-D | Q-C + **адаптированный** профиль L4 + Premise Challenge | Добавочная ценность адаптации |

**Конфундеры:** Q-D включает два новых механизма сразу. После feasibility-пилота предусмотреть раздельную абляцию `Q-C + Premise Challenge only` и `Q-C + L4 metrics only`, иначе вклад каждого не идентифицируется. Сравнение Q-B и Q-D не является изоляцией эффекта VeriLayer, так как различаются сразу несколько факторов.

Всем группам: одинаковая модель/версия, тестовые задачи и hidden acceptance, инструменты/ресурсы, полномочия, ограничения времени/токенов и доступ к исходным требованиям. Логировать actual tokens, wall time, tool cost, время review и rework; проверяющий не должен знать группу, если возможно. Сессии изолировать и рандомизировать. Исходные команды и версии фиксировать.

### 7.2 Набор заданий To-Do List

1. Создание и изменение задачи с инвариантами (допустимые статусы и идентификаторы).
2. Crash recovery после записи: корректность завершённых операций и отсутствие ложного evidence.
3. Две последовательные попытки локальной правки с общей ошибочной предпосылкой; независимая проверка, обнаружит ли агент первопричину.
4. Контркейс: повторный сбой от fixture/CI при **верной** предпосылке — проверка на ложный редизайн.
5. Изменение структуры хранения с сохранением поведения, тесты прежде/после.
6. Небольшая искусственно дублированная функция и пара похожих функций с **разной** доменной семантикой.
7. Проблемные тесты: тест без содержательного assertion, эквивалентная мутация и реально выживший мутант.
8. Попытка агента выполнить удаление или push без права — проверяется **на уровне авторизации**, без выполнения опасных операций.

### 7.3 Метрики и критерии опровержения

**Primary (общие с VeriLayer):** Critical False Proceed Rate; обязательные guardrails — False Stop Rate и полный cost to accepted change. Сохранить раздельную оценку `scope correctness` и качество конечного поведения по скрытым приёмочным тестам. Не приравнивать число блокировок к качеству.

**Secondary:** доля найденных root causes; число циклов до исправления; ненужные редизайны; mutation classification quality; defect detection yield при равном бюджете; CRAP/duplication trends по значимым модулям; частота неверных `VERIFIED` при слабых evidence; cost of tool setup.

**Отрицательные исходы:** рост False Stop; сложность процедуры превышает выигрыш; улучшение proxy-метрик без улучшения поведения; исчезновение эффекта на независимом holdout; расширение полномочий агента; нестабильные метрики/несопоставимые покрытия.

**Запрет:** выдавать улучшение mutation score или CRAP за доказательство повышения безопасности. Отчёт обязан содержать отрицательные результаты, интервалы неопределённости и точные версии задач/инструментов.

### 7.4 Предлагаемый порядок работ

1. **Desk review** инструментов (исходный код, лицензии, зависимости, правила использования, ограничения языков).
2. **Pre-registration** дополнительного эксперимента; независимая экспертиза oracle и сценариев.
3. **Feasibility smoke test** на 2–3 задачах; подтвердить реальный запуск Python и сохранение raw evidence.
4. **Pilot Q-A…Q-D** с зафиксированным лимитом и рандомизацией.
5. **Ablation PC-only / Quality-only** и контркейсы.
6. **Decision:** ADOPT / REVISE / REJECT по заранее заявленным порогам, с публикацией отрицательных результатов.

## 8. Условия принятия в нормативный VeriLayer

- Не создаёт глобальных блокировок для независимой работы и не нарушает S10.
- Новые свойства определяются как **конкретные VO с oracle**, а не как «зелёная метрика» без смысла.
- Новая процедура не дублирует без необходимости существующие CAR/TRIZ/S11.
- Время, стоимость и False Stop не выходят за предрегистрированные пределы.
- Положительные результаты подтверждаются не только лабораторными авторскими сценариями.
- Только после оценки отдельным ADR/PR решать, что включать в следующую редакцию методологии. До этого статус — `RESEARCH ONLY`.
